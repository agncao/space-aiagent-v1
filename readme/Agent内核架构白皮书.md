## 1. 产品定位

### 1.1 一句话定位

> **提供一款具备任务编排能力的航天 AI 助理，内置通用工具能力，并支持客户/合作伙伴通过 Skill 文档扩展垂直业务流程。客户既能直接使用内置能力，也能自行编写 Skill，还能购买产品方或第三方的 Skill 包。**

### 1.2 定位内涵

这不是一个"什么都懂的航天 AI"，也不是一个"针对单一场景的垂直应用"，而是 **"平台 + 扩展"** 的混合定位：

| 维度 | 选择 | 反面 |
|------|------|------|
| 通用 vs 垂直 | **平台化通用内核 + 垂直扩展机制** | 不是"轨道分析专用 AI"或"覆盖分析专用 AI" |
| 封闭 vs 开放 | **协议开放，实现封闭** | 不是"客户只能用我们写的功能" |
| 产品 vs 项目 | **可售卖的标准产品** | 不是"每个客户重新定制开发" |

### 1.3 为什么航天领域适合这个定位

1. **需求极度垂直**：805 所的轨道分析流程 ≠ 804 所 ≠ 商业航天公司 ≠ 高校。产品方不可能为每家定制
2. **客户有保密流程**：很多内部 SOP、专业判断不能写到通用产品里，但客户自己加载没问题
3. **领域知识在客户脑里**：客户的工程师比产品经理更懂"轨道机动该怎么规划"。产品方不应假装懂所有航天专业流程
4. **商业延展性**：基础产品卖一遍，垂直 Skill 可以做咨询服务/定制开发二次变现

### 1.4 产品边界

| 由产品方提供 | 由客户提供 |
|------------|----------|
| Agent 内核（任务编排引擎、中间件机制） | 业务流程 Skill 文档（垂直场景的 SOP）|
| 通用工具能力（场景管理、实体管理、轨道管理等）| 私有数据源接入（如内部 API、数据库）|
| Skill 加载框架与协议规范 | Skill 内的领域专业判断 |
| Skill 开发规范文档与示例 | 内部审核与发布流程 |
| 基础 Skill 示例库（5-10 个开箱即用） | 业务定制 Skill |

## 2. 目标架构

### 2.1 四层 + 横切关注点

```
┌──────────────────────────────────────────────────────────────┐
│                      客户扩展层                              │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
│  │ 客户 A skill │  │ 客户 B skill │  │ 第三方 skill │       │
│  │ (805 所)     │  │ (商业航天)   │  │ (合作伙伴)   │       │
│  └──────────────┘  └──────────────┘  └──────────────┘       │
└──────────────────────────────────────────────────────────────┘
                              ↕ Skill 协议（见第 7 节）
┌──────────────────────────────────────────────────────────────┐

│                                                              │
│  ┌──── 任务编排引擎 ────────────────────────────────┐       │

│  └──────────────────────────────────────────────────┘       │
│                                                              │
│  ┌──── 横切关注点 ──────────────────────────────────┐       │
│  │ 多租户隔离 / 权限 / 审计 / 可观测性 / 多模型      │       │

│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐        │
│  │ 覆盖分析 │ │ 可见性   │ │ 报告生成 │ │ 计算服务 │ 产品方 │

│  └──────────────────────────────────────────────┘           │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐

└──────────────────────────────────────────────────────────────┘
```

### 2.2 各层职责

| 层 | 职责 | 边界 |
|----|------|------|
| **客户扩展层** | 客户/第三方提供的垂直能力 | 只能通过协议接入，不能侵入内核 |
| **Agent 内核层** | 意图理解、任务编排、状态管理、工具调度、失败恢复、结果整合 | 不含任何业务领域知识 |
| **能力层** | 原子业务能力（工具函数）| 单一职责，可被任意 Skill/Agent 调用 |
| **前端执行层** | 业务逻辑真正执行（Cesium 操作、计算等）| 不含 AI 推理 |

### 2.3 关键设计原则

1. **协议优先于实现**：层与层之间通过明确协议交互（Skill 协议、Tool 协议、WebSocket 协议），不依赖具体实现
2. **内核零业务知识**：Agent 内核不应包含任何航天领域硬编码逻辑，所有领域知识通过 Skill/工具/Memory 注入
3. **能力正交可组合**：每个工具是原子能力，Skill 是工具的组合配方，工具之间无隐式依赖
4. **失败可观测可恢复**：每一层都必须暴露状态、可被监控、可从失败中恢复

## 3. 五个关键架构决策点

### 3.1 决策 1：Skill 路由策略

**问题**：用户提出"分析北斗覆盖"时，Agent 如何知道该加载 `coverage_analysis.md` 而不是 `visibility_analysis.md`？

**候选方案对比**：

| 方案 | 适合场景 | 代价 |
|------|---------|------|
| 全量注入 prompt | skill ≤ 20 个 | prompt 膨胀、token 成本 |
| **LLM 主动检索（按需加载）** | **企业级、skill 数 10-100+** | **多一轮 LLM 调用、有选错风险** |
| 关键词触发 | 流程明确、触发词清晰 | 维护成本高、跨语言困难 |
| 向量检索 + LLM 重排 | skill 数 100+ | 实现复杂、需要向量库 |

**决策：LLM 主动检索（按需加载）**

**决策依据**：
1. **Claude Code 验证过**：Anthropic 自家的 Claude Code 用此模式，证明在 20-50 个 skill 规模下可靠（参考本次对话开头的 skill 元数据列表 + Skill 工具机制）
2. **Token 经济性**：元数据轻量注入（10 个 skill 约 1-2k token），完整内容按需加载（避免 20k+ token 膨胀）
3. **扩展性**：未来 skill 增多时，可平滑升级到"向量检索 + LLM 重排"，不破坏协议
4. **灵活判断**：LLM 可判断"不需要 skill 直接回答"，比关键词触发更智能

**实现机制**（详见第 7 节）：
- 启动时把 skill 的 `name + description` 注入 system prompt
- 暴露 `load_skill(skill_name)` 工具
- LLM 根据用户意图判断后调用工具加载完整内容

**风险与对策**：
- **风险**：LLM 选错 skill
- **对策**：description 写清楚触发场景；后续可加"置信度低于阈值时反问用户"

### 3.2 决策 2：Skill 是否能引用客户私有工具

**问题**：客户 Skill 文档里能否引用产品方未提供的工具（如客户内部 API）？

**候选方案**：

| 方案 | 客户扩展性 | 实现复杂度 | 安全风险 |
|------|----------|----------|---------|
| **保守方案**：skill 只能用产品方工具 | 受限 | 低 | 低 |
| **激进方案**：skill 可引用客户私有工具 | 高 | 高（需插件机制+沙箱） | 中 |

**决策：当前版本采用保守方案，协议预留激进方案扩展点**

**决策依据**：
1. **第一版优先稳定**：客户工具插件机制涉及代码执行、沙箱隔离、版本兼容，复杂度过高
2. **协议要前向兼容**：Skill frontmatter 中保留 `tools_required` 字段，未来开放时不破坏已有 skill
3. **客户期望管理**：在《Skill 开发规范》中明确写"当前版本仅支持引用内置工具"，避免期望落空

**何时升级到激进方案**：
- 多个客户提出"想接自己 API"的强需求
- 内置工具集稳定，无频繁变动
- 沙箱方案经过安全审计

### 3.3 决策 3：多租户隔离

**问题**：卖给多家客户时，如何保证客户 A 的 skill 不泄露给客户 B？

**部署模式判断**：
- 航天领域客户（院所、军工、商业航天）**绝大多数要求私有化部署**
- 不存在"多客户共享一个 SaaS 实例"的场景

**决策：单租户架构 + 用户级权限**

**决策依据**：
1. **私有化部署是行业硬约束**：客户数据不能上云
2. **简化架构**：不需要做租户隔离、加密存储、跨租户审计
3. **复杂度降低 10 倍**：从"多租户 + 用户权限"简化为"用户/角色权限"

**保留能力**：
- 同一部署内不同用户的权限差异（如普通用户 vs 管理员）
- 不同用户能用的 skill 集合可配置

### 3.4 决策 4：Skill 是否能调用其他 Skill（嵌套/组合）

**问题**：Skill A 的某步骤能否调用 Skill B？

**候选方案**：

| 方案 | 能力 | 风险 |
|------|------|------|
| 不允许嵌套 | 简单，能力有限 | 无法组合复杂流程 |
| **受控嵌套**（限制深度、禁止循环）| **强大，可组合** | **需要循环检测** |
| 自由嵌套 | 最强大 | 容易死循环、Stack Overflow |

**决策：受控嵌套（限制深度 ≤ 3，禁止循环引用）**

**决策依据**：
1. **企业级产品必须支持组合**：复杂航天流程往往由多个子流程组成
2. **受控嵌套是行业惯例**：编程语言的函数调用栈、工作流引擎都是这套机制
3. **循环检测可做**：维护"当前调用栈"，新加载 skill 前检查是否已在栈中

**实现要点**：
- `load_skill` 工具维护调用栈（在 state schema 中）
- 深度超过阈值返回错误
- 检测到循环引用返回错误并提示用户

### 3.5 决策 5：Skill 版本管理与生命周期

**问题**：Skill 怎么升级？老版本怎么回滚？谁能发布 Skill？

**决策：采用"目录即版本"的简单方案 + 文件级审计**

**版本管理机制**：
- 每个 Skill 一个 markdown 文件，文件名即 skill name
- 修改即覆盖（不做 git 级版本管理）
- 通过文件系统备份/快照实现回滚（部署运维层负责）
- Skill frontmatter 中 `version` 字段记录当前版本号

**生命周期**：

```
开发 → 测试 → 部署 → 监控 → 升级/退役
```

| 阶段 | 机制 | 工具支持 |
|------|------|---------|
| 开发 | 客户按规范写 markdown | 提供 Skill 模板、《开发规范》文档 |
| 测试 | CLI 校验格式 + 触发测试 | `python -m space_aiagent.cli skill validate xxx.md` |
| 部署 | 文件放入 `skills/` 目录即生效 | 配置热加载（暂不做，重启生效）|
| 监控 | 加载日志、调用次数、成功率 | 可观测性系统（Phase 1A）|
| 升级 | 覆盖原文件 + 重启 | 文件备份机制 |
| 退役 | 删除文件 + 重启 | 配置清理 |

**权限模型**：
- 谁能放 Skill 到 `skills/` 目录：通过文件系统权限控制
- 不在 Agent 内做发布权限（避免过度工程）

## 4. Agent 内核成熟度模型

### 4.1 成熟度等级定义

| 等级 | 特征 | 关键能力 |
|------|------|---------|
| **L0** | DEMO 级 | 单 Agent + 工具列表 |
| **L1** | 多 Agent 协作 | 多 Agent + 子 Agent 路由 |
| **L2** | 状态化 | + State Schema + 中间件机制 |
| **L3** | 可扩展 | + Skill 加载/路由 |
| **L4** | 企业级入门 | + 完整可观测性 + 多模型 + 失败恢复 |
| **L5** | 成熟平台 | + 多租户/用户权限 + 客户工具插件 + Skill 市场 |
| **L6** | 行业领先 | + 自适应编排 + 学习反馈 + 多模态 |

### 4.2 当前位置评估

**当前等级：L3 雏形（L2 稳定，部分 L4 横切能力已提前落地）**

**已具备的 L2 能力**：
- ✅ Orchestrator + YAML 声明式子 Agent 路由
- ✅ State Schema 跨 task 边界同步（`current_scene_name`）
- ✅ 中间件链（PrimaryAgentMiddleware / SubagentToolValidationMiddleware / RetryMiddleware）
- ✅ Task loop guard（防连续 task 死循环）
- ✅ 结构化输出（ToolStrategy + AgentResponse）
- ✅ SSE + POST 传输及 SQLite checkpointer 持久化
- ✅ 声明式 Human-in-the-loop（`interrupt_on` + `/resume`）

**已具备的 L3 能力（雏形）**：
- ✅ Skill Package 层（内置 SkillsMiddleware + CompositeBackend `/skills/` 路由 + progressive disclosure）
- ✅ 3 个内置 Skill：`open-scenario`、`query-scenario`、`add-entity`
- ❌ Skill 基础审计与稳定的校验/回归测试（当前下一任务）
- ❌ Skill Backend/Policy 层（CommandGuard、脚本沙箱、完整审计；待首个带 `scripts/` 的 Skill 驱动）

**已提前具备或仍缺失的 L4 能力**：
- ✅ AI 维度 trace（OTel + Langfuse，每步耗时 + token 归因）—— Phase 1A-1
- ✅ 失败自动重试与降级（RetryMiddleware）—— Phase 1B
- ❌ 系统 Metric（成功率、失败率、QPS/延迟）—— Phase 1A-2
- ❌ 多模型动态选择（主/Flash 模型工厂已具备，完整动态路由未做）

**当前暂不计为已完成的能力**：
- 后端场景依赖 fail-fast 当前被临时关闭，最终由前端工具结果兜底。
- `SceneAgentHitlMiddleware` 当前未挂载，自定义 `hitl_select` / `hitl_yn` 只保留协议兼容。
- 旧的 pending_intent 意图捕获与自动续接已移除。

### 4.3 目标等级

**12 个月目标：稳定在 L4，部分 L5 能力**

| 能力域 | 目标等级 |
|--------|---------|
| 任务编排 | L4（强编排 + 失败恢复）|
| Skill 系统 | L3（完整加载/路由/审计）|
| 可观测性 | L4（trace + metric + audit log）|
| 多模型 | L4（Flash 路由 + 主模型执行）|
| 权限 | L5 简化版（用户/角色，不做多租户）|
| 客户工具插件 | 暂不实现，协议预留 |

**不追求 L6**：自适应编排和学习反馈是研究型能力，企业级产品稳定优先。

## 5. 横切关注点（比 Skill 加载更重要）

> **核心认知**：Skill 系统建立在 Agent 内核之上。内核不扎实就加 Skill，等于在沙地上盖楼。这一节描述的能力，**优先级全部高于 Skill 系统**。

### 5.1 可观测性（最高优先级）

**为什么最重要**：
- 没有 trace，Skill 选错都不知道
- 没有 metric，无法判断系统健康度
- 没有 audit log，企业客户不敢用

**目标能力**：

| 维度 | 内容 |
|------|------|
| **Trace** | 每次会话的完整调用链（用户输入 → 意图识别 → Skill 加载 → 工具调用 → 结果返回），含每步耗时 |
| **Metric** | 系统级（QPS/延迟/错误率）+ 业务级（Skill 使用次数、工具调用分布、用户满意度）|
| **结构化日志** | JSON 格式，可接入 ELK，支持按 thread_id / user_id / skill_name 检索 |
| **调试视图** | 单次会话的"X-Ray 视图"——可视化展示 LLM 推理、工具调用、状态变化 |

#### 架构原则：可观测性对业务零依赖

> **强约束**：可观测性系统（Langfuse / Prometheus / Grafana）对业务系统**零依赖**。即便可观测性组件全部宕机，业务系统必须照常运行。

实现机制：
- **OpenTelemetry 标准协议**：业务代码用 OTel API，不直接调平台 SDK
- **配置层总开关**：`observability.enabled: false` 时不初始化 OTel，全局使用 NoOp Tracer，业务代码零开销
- **Exporter 失败容错**：OTel Exporter 后端不可达时默认重试后放弃，记 warning 日志，**绝不抛异常到业务层**
- **异步发送**：trace 数据异步发送，主业务流程不阻塞

客户运维价值：可观测性组件可以独立重启/升级，不需要协调业务方停机。

#### 推荐组合（最终目标架构）

按"AI 维度 + 系统维度"分层选型，基于 OpenTelemetry 标准避免锁定：

```
Agent 应用层（LangGraph + deepagents）
        ↓ OTel API（不直接调平台 SDK）
OpenTelemetry 标准（协议层，可换后端）
        ↓
┌──────────────────┬──────────────────┬────────────────┐
│ Langfuse（自部署）│ Prometheus       │ Loki           │
│ - LLM trace      │ + Grafana        │ + Grafana      │
│ - prompt/response│ - 系统指标       │ - 结构化日志   │
│ - token 成本     │ - QPS/延迟       │ - 聚合查询     │
│ - Skill 路由     │                  │                │
└──────────────────┴──────────────────┴────────────────┘
```

**选型决策依据**：

| 平台 | 角色 | 为什么选它 |
|------|------|----------|
| **OpenTelemetry** | 协议层 | 标准化，未来可换后端，避免锁定 |
| **Langfuse（自部署）** | AI 维度 trace | LLM 专项（看 prompt/response），私有化部署满足航天数据保密要求 |
| **Prometheus** | 系统指标 | 系统级 QPS/延迟/资源监控，事实标准 |
| **Grafana** | 统一可视化 | 一个面板看 Langfuse + Prometheus + Loki，跨数据源关联 |
| **Loki** | 日志聚合 | 与 Grafana 同生态，轻量级 |

**不选其他方案的理由**：
- ❌ **LangSmith SaaS**：数据出境问题，航天客户验收过不了
- ❌ **Datadog / New Relic**：商业 SaaS，按 host/trace 计费，长期成本高 + 数据出境
- ❌ **自建 ClickHouse 全家桶**：维护成本高，团队规模不支持

技术细节与对比详见 [`readme/python教程.md`](python教程.md) 第 26 章「可观测性」。

### 5.2 失败恢复

**典型失败场景**：

| 场景 | 当前行为 | 目标行为 |
|------|---------|---------|
| 工具调用超时 | 直接失败 | 自动重试 3 次，仍失败则降级 |
| LLM 返回非法 JSON | Pydantic ValidationError | 降级为 OUT_OF_SCOPE + LLM 原文本兜底 |
| Skill 加载失败 | 整个会话失败 | 跳过该 Skill，回退到无 Skill 模式 |
| 子 Agent 死循环 | Task loop guard 兜底 | + 用户提示 + 状态回滚 |
| 前端 WebSocket 断开 | 会话中断 | 状态持久化，重连后恢复 |

### 5.3 多模型

**策略：按任务复杂度动态选择**

| 任务类型 | 模型 | 理由 |
|---------|------|------|
| Skill 路由判断 | Flash LLM | 简单分类任务，省钱 |
| 子 Agent 类型分类 | Flash LLM | 同上 |
| 主流程推理（Orchestrator）| 主 LLM | 需要强推理 |
| 工具参数提取 | Flash LLM | 结构化任务 |
| 复杂专业计算（轨道机动等）| 主 LLM 或专用模型 | 需要专业知识 |

**实现要点**：
- 已有 `build_model()` + `build_flash_model()` 基础
- 需要扩展为"按任务类型路由"的中间件或工具
- Skill frontmatter 可声明 `model_preference`，让 Skill 作者指定模型

### 5.4 审计

**审计粒度**：

| 事件类型 | 审计字段 |
|---------|---------|
| 用户登录 | user_id, timestamp, ip |
| Skill 加载 | user_id, skill_name, version, trigger_source（自动/手动）|
| 工具调用 | user_id, tool_name, args, result_summary, duration |
| 失败事件 | user_id, error_type, context, recovery_action |
| 配置变更 | user_id, changed_field, old_value, new_value |

**审计日志独立于业务日志**，单独存储、单独查询、不可篡改（追加写入）。

### 5.5 权限

**简化模型（不做多租户）**：

| 角色 | 能力 |
|------|------|
| 普通用户 | 使用内置工具 + 公开 Skill |
| 高级用户 | + 创建/修改自己的 Skill |
| 管理员 | + 管理所有 Skill + 查看审计日志 + 配置变更 |

**实现**：基于角色的访问控制（RBAC），权限校验在中间件层。

### 5.6 成本控制

**目标**：

| 维度 | 实现方式 |
|------|---------|
| 按 Skill 归因 token 成本 | Skill 加载时记录起始 token，结束时计算消耗 |
| 按用户归因成本 | 审计日志聚合 |
| 按会话归因成本 | thread_id 维度聚合 |
| 成本告警 | 单次会话超过阈值时告警 |

### 6.2 每个阶段的决策依据

#### Phase 1A 优先做可观测性的原因

**决策依据**：
1. **后续一切依赖可观测性**：失败恢复需要 trace 定位、Skill 路由需要 metric 评估、审计需要日志基础
2. **当前 LoggingMiddleware 已退役**：可观测性职责由 PrimaryAgentMiddleware 内联日志承担，但覆盖不全，没有 trace 和 metric
3. **企业客户准入要求**：航天客户验收产品时，可观测性是硬指标
4. **不可观测的系统不可维护**：Skill 系统上线后故障排查会非常困难

**为什么不先做 Skill**：没有 trace 的 Skill 系统，出问题时只能靠 print 调试，开发效率极低。

**为什么 Phase 1A 拆成三个子阶段（1A-1 / 1A-2 / 1A-3），且执行顺序分散在整体路线中**：

| 子阶段 | 执行位置 | 决策依据 |
|--------|---------|---------|
| **1A-1** | 最先（已完成）| AI 维度 trace 是核心价值，也是失败恢复（1B）定位故障的前置依赖，先跑通主战场 |
| **1A-2** | 延后至 Phase 1C 之后 | AI 维度 trace（1A-1）已足够支撑开发期故障定位与失败恢复；系统级 QPS/延迟监控对当前阶段价值有限，等业务功能（1B / Phase 2 / 1C）稳定、有真实流量后再补，避免过早引入基础设施 |
| **1A-3** | 延后至 Phase 3 之后 | Grafana 的价值是跨数据源关联（Langfuse + Prometheus + Loki）+ 面向客户展示，需多个数据源就绪才有意义；调试期 Langfuse UI + Prometheus 自带页面够用，故放最后 |

**核心原则**：拆开做避免一次性引入过多基础设施，按"真正需要时才上"推进。

#### Phase 1B 紧跟 Phase 1A-1 的原因

**决策依据**：
1. **失败恢复依赖 trace**：要知道哪里失败、为什么失败，才能设计恢复策略
2. **Skill 系统需要失败恢复托底**：Skill 加载失败、工具调用失败都需要降级路径
3. **当前只有 task loop guard 一层兜底**：远远不够企业级标准

#### Phase 2 Skill 系统第一版的设计

**包含内容**：
- Skill frontmatter 协议（Anthropic 风格 YAML + Markdown）
- SkillsMiddleware（LLM 主动检索模式）
- `load_skill` 工具
- 3-5 个示例 Skill（add_satellite / coverage_analysis / visibility_analysis 等）
- **多模型路由**（从 Phase 1 提前到这里）
- **基础 Skill 审计日志**（从 Phase 5 前移到这里）

**为什么多模型从 Phase 1 提前到 Phase 2**：
1. Skill 路由本身需要 LLM 判断，这一步用 Flash 模型省钱
2. 主流程用主模型，路由判断用 Flash 模型，天然耦合
3. Skill 系统上线后立即产生 token 成本，多模型能立即省钱

**为什么审计从 Phase 5 前移到 Phase 2**：
1. Skill 一上线就需要审计"谁用了哪个 Skill"
2. Skill 加载失败的原因需要记录
3. 用 Phase 1A 的 trace 机制顺便实现，成本低

**为什么选 LLM 主动检索而非全量注入**：
详见第 3.1 节决策依据。

**为什么选 Anthropic 风格 Skill 文档**：
1. 客户是航天工程师不是软件工程师，markdown + YAML 是他们能接受的复杂度上限
2. Anthropic 风格生态成熟，有大量参考案例
3. JSON Schema 风格虽然机器可解析，但写作门槛高

#### Phase 1C 工具能力补全放在 Phase 2 之后的原因

**决策依据**：
1. **Skill 会暴露工具缺口**：写示例 Skill 时会自然发现"缺少 XX 工具"
2. **避免预先猜测**：先做 Skill 让真实需求浮出水面，比预先猜要做什么工具更准
3. **工具补全不影响架构稳定**：可以并行做，不阻塞其他阶段

#### Phase 5 横切关注点（简化版）的原因

**简化内容**：
- 不做多租户（私有化部署，详见第 3.3 节决策）
- 用户/角色权限简化为三级（普通/高级/管理员）
- Skill 版本管理用"目录即版本"

**保留内容**：
- 完整审计（基于 Phase 2 基础审计扩展）
- 权限模型
- Skill 生命周期管理

#### Phase 3 暂缓的原因

**决策依据**：
1. **第一版优先稳定**：客户工具插件机制涉及代码执行、沙箱隔离，复杂度过高
2. **协议预留**：Skill frontmatter 中保留 `tools_required` 字段，未来开放时不破坏兼容
3. **客户期望管理**：在《Skill 开发规范》中明确"当前版本仅支持内置工具"

**何时启用 Phase 3**：
- 多个客户提出"想接自己 API"的强需求
- 内置工具集稳定
- 沙箱方案经过安全审计

### 6.3 阶段间的不变量

无论在哪个阶段，以下原则不变：

1. **协议优先**：每加一个能力，先定协议再写实现
2. **内核零业务知识**：航天领域逻辑全部在 Skill/工具/Memory 里
3. **可观测优先**：任何新功能必须先考虑怎么 trace、怎么 metric
4. **失败可恢复**：任何新功能必须设计失败降级路径
5. **客户期望管理**：未实现的能力要在文档中明确说明边界

## 7. Skill 系统设计

### 7.1 Skill 文档格式（Anthropic 风格）

采用 YAML frontmatter + Markdown body 的格式：

```markdown
---
name: orbit_maneuver_planning
description: LEO 到 GEO 转移的轨道机动规划流程，含燃料计算和霍曼转移判断
trigger_keywords: [轨道转移, 机动, 霍曼, LEO, GEO, 转移轨道]
tools_required: [create_orbit_maneuver, calculate_delta_v]
model_preference: primary  # primary / flash，可选，默认 primary
version: 1.0.0
author: 805-institute
---

# 轨道机动规划流程

## 适用场景
本 Skill 用于规划低地球轨道（LEO）到地球同步轨道（GEO）的转移任务。

## 触发条件
用户提到以下关键词时加载：
- "轨道转移"、"LEO 到 GEO"、"霍曼转移"
- "卫星变轨"、"轨道提升"

## 操作步骤

### 步骤 1：确认转移类型
询问用户：
- 是否标准霍曼转移（最省燃料，耗时 5 小时左右）
- 是否快速转移（多脉冲，省时但耗燃料）

### 步骤 2：收集源轨道参数
调用 `query_current_orbit` 工具，获取当前轨道根数。

### 步骤 3：计算转移参数
调用 `calculate_delta_v` 工具，输入：
- 源轨道半长轴
- 目标轨道半长轴（GEO 默认 42164 km）
- 转移类型

### 步骤 4：创建机动段
调用 `create_orbit_maneuver`，参数从前序步骤填充。

## 失败处理
- 步骤 2 失败：提示用户检查卫星是否在轨
- 步骤 3 失败：建议用户手动提供半长轴
- 步骤 4 失败：检查燃料是否足够
```

### 7.2 元数据字段规范

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `name` | string | ✅ | 全局唯一，kebab-case，作为 `load_skill` 的参数 |
| `description` | string | ✅ | 一句话简介，注入 system prompt 供 LLM 判断 |
| `trigger_keywords` | list[string] | 推荐 | 触发关键词，用于辅助 LLM 判断（不强制）|
| `tools_required` | list[string] | 可选 | 依赖的工具名列表，当前版本仅用于校验（未来 Phase 3 用）|
| `model_preference` | enum | 可选 | `primary` / `flash`，默认 `primary` |
| `version` | string | 推荐 | 语义化版本号 |
| `author` | string | 推荐 | 作者标识 |

### 7.3 LLM 主动检索机制

**两阶段加载**：

#### 阶段 1：元数据注入（启动时）

启动 Agent 时扫描 `skills/` 目录，解析所有 Skill 的 frontmatter，构造元数据列表注入 Orchestrator 的 system prompt：

```markdown
## 可用 Skills

按需调用 `load_skill` 工具加载完整内容。判断规则：
- 用户意图匹配某 Skill 的 description → 调 load_skill
- 用户明确说"用 X skill" → 调 load_skill
- 不确定是否需要 Skill → 不调，直接回答

### Skill 列表
- add_satellite: 添加卫星到场景，支持 SSC 编号/名称/国籍/TLE 多路径输入
- coverage_analysis: 区域覆盖分析，含响应时间和重访时间计算
- orbit_maneuver_planning: LEO-GEO 轨道机动规划
- visibility_analysis: 地面站对卫星的可见性分析
- ...
```

#### 阶段 2：按需加载（运行时）

LLM 判断需要某 Skill 时，调用 `load_skill` 工具：

```python
@tool
def load_skill(skill_name: str) -> str:
    """
    按需加载完整 Skill 文档。
    
    Args:
        skill_name: Skill 的 name 字段（来自可用 Skill 列表）
    
    Returns:
        Skill 完整内容（markdown），按文档步骤执行
        
    Raises:
        ValueError: skill_name 不存在
        RuntimeError: 嵌套深度超过限制（3 层）
        RuntimeError: 检测到循环引用
    """
```

### 7.4 Skill 路由的中间件实现

`SkillsMiddleware` 的核心职责：

| 职责 | 实现位置 |
|------|---------|
| 启动时扫描 skill 目录、解析 frontmatter | middleware 初始化 |
| 把 skill 元数据列表注入 system prompt | `awrap_model_call` 前置 |
| 提供 `load_skill` 工具 | 注册为 Agent 工具 |
| 维护 Skill 调用栈（防循环）| state schema 字段 |
| 记录 Skill 加载审计日志 | `awrap_tool_call` 后置 |

### 7.5 显式调用支持

支持用户通过斜杠命令显式触发 Skill：

```
前端→后端: {type: "user_input", content: "/orbit_maneuver", ...}
→ 后端识别斜杠命令 → 直接调 load_skill，不走 LLM 判断
```

**好处**：
- 高级用户可强制使用某 Skill
- 调试时方便测试 Skill
- 减少不必要的 LLM 推理（省钱）

## 8. 关键认知（防漂移清单）

> 这一节记录讨论过程中确认的关键认知，防止后续开发中 drift。

### 8.1 关于 Skill 的认知

1. **Skill ≠ 强制流程**：Skill 本质是 prompt 文档，不消除 LLM 不可靠性。要强制流程必须用代码（复合工具）
2. **Skill 是"教 LLM 怎么做"**：不是"让 LLM 能做什么"。后者是 Tool 的职责
3. **Skill 越简单越好**：Agent 内核越强大，Skill 越简单（只需补充专业判断，不用负责流程控制）
4. **Skill 不是代码执行**：Skill 是 markdown 文档，不执行任意代码（这是它和 Tool 插件的本质区别）
5. **Skill 是客户扩展点**：产品方提供框架，客户提供内容

### 8.2 关于 Agent 内核的认知

1. **任务编排是 Agent 的灵魂**：不能依赖 Skill 驱动流程，Agent 必须自己有编排能力
2. **Agent 内核零业务知识**：所有领域知识通过 Skill/Tool/Memory 注入
3. **可观测性优先于扩展性**：不可观测的系统不可维护
4. **失败恢复是企业级底线**：没有失败恢复的 Agent 不能上生产

### 8.3 关于产品边界的认知

1. **平台 + 扩展定位**：不是垂直应用，不是通用 AI，是"通用内核 + 垂直扩展"
2. **协议优先于实现**：每加一个能力，先定协议再写实现
3. **客户期望管理**：未实现的能力要在文档中明确说明边界
4. **企业客户验收硬指标**：可观测性、审计、失败恢复——这些比功能丰富度更重要

### 8.4 关于决策追溯的认知

1. **LLM 主动检索 > 全量注入**：基于 Claude Code 验证 + Token 经济性
2. **暂缓客户工具插件**：基于复杂度 vs 价值评估，协议预留扩展点
3. **单租户架构**：基于航天客户私有化部署的硬约束
4. **受控嵌套（深度 ≤ 3）**：基于企业级产品必须支持组合的需求
5. **目录即版本**：基于客户运维能力，不做 Git 级版本管理

## 附录 A：术语表

| 术语 | 定义 |
|------|------|
| **Agent** | 能感知环境、做出决策、调用工具完成任务的智能体 |
| **Skill** | Markdown 格式的流程指导文档，教 LLM 在特定场景下按步骤工作 |
| **Tool** | Python 函数，作为 LLM 的原子能力，可被调用并返回结构化数据 |
| **Orchestrator** | 主控 Agent，负责意图识别、子 Agent 路由、任务编排 |
| **Middleware** | 中间件，包裹 Agent 的 LLM 调用/工具调用，提供横切能力 |
| **State Schema** | 跨节点状态定义，自动在父子 Agent 间同步指定字段 |
| **Task Orchestration** | 任务编排，把高层意图拆解成有序的原子步骤 |
| **Backend** | deepagents 的文件 I/O 适配器（FilesystemBackend / SandboxBackend 等）|
| **Memory** | 通过 Backend 加载到 system prompt 的领域知识（如 AGENTS.md）|
